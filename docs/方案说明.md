# 方案说明

本文是这套业务知识库方法的说明存档，与仓库根目录的介绍和 `skills/` 中的四个技能正文一致。整理于 2026-11-13。这里写的是方法，不是某个具体业务的机密材料。

## 要解决什么问题

进入一个新业务时，材料通常又多又乱：权威手册、培训稿、设计稿、价盘、一线口头承诺、会议记录和竞品材料会叠在一起。如果把它们直接堆进一个资料库，用的时候很容易把「曾经培训过的」讲成「现在已上线」，或把尚未拍板的数字讲成现行口径。

这套方法约定：助手按固定流水线学习整理，知识靠一组互相链接的核心文件积累，而不是靠聊天和散落的笔记。使用者不用自己分类和维护链接，只在定边界、确认拟改和拍板时出手。

## 方法从哪里来

主干与 [Karpathy 的 LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 一致：原文不动，先编译成可引用的页面，用目录和日志维护，并定期体检。同时吸收了：

- [Diátaxis](https://www.diataxis.fr/)：按使用需求组织，一页只服务一种需要
- 销售内容治理：对外主张单独登记，并按材料易变程度复审
- 编译层加证据链的做法，例如 [LangChain 对 OpenWiki 的讨论](https://www.langchain.com/blog/building-agent-memory-openwiki-graphs)、[wiki 与 RAG 分层的讨论](https://maskin.io/docs/llm-wiki-vs-rag/)
- 企业知识里「指向权威源、受控回写、少做会过期的副本」的思想

明确不采用的有两件事：用外网搜索去补业务死数；以及把所有文件复制进一个新中心，让副本冒充权威原文。

## 进入一个新业务时怎么建

按阶段建，不求一次穷尽。

1. **定边界。** 明确这个业务是什么、权威资料在哪、谁来拍板口径，以及眼下最主要的两到四种用法。同时立下纪律：不编造、冲突先挂起、设计不等于上线、培训不等于可讲、案例不等于证据、内部系统不等于对外卖点。
2. **有边界地收原料。** 先收权威稿、当前培训或手册、现行价盘或合同、最近的经营材料，以及会直接影响口径的一线说法。历史资料按后面作业的需要再补。
3. **编译三个底座。** 只写现状的业务图景；带状态的能力与边界清单；口径三态和主张登记册，已冲突的数字与承诺先挂到待确认。
4. **先建高频用法入口。** 大多数业务会先建封装、赋能、建设、把关这四个。
5. **用起来再反补。** 每做一次真实作业就按检索路径走，缺页就补页，新冲突就上台账。权威稿只有在明确授权、且对应问题已经拍板之后，才回写。

第一轮最小闭环见主技能。之后每次交文件，都按同一套办法学进去，库是积累起来的，不是每次重做的。

## 技能如何使用

把本仓库中的四个 `SKILL.md` 放到助手可加载的技能库中。日常约定：

- 建库或丢来一批文件：先走「业务知识库」，再走「学习入库」
- 按某个用法出方案、赋能、建设、把关或查询：走「用法检索」
- 到了例行检查日：走「定期校验」

四个技能的完整执行约定以 `skills/` 目录中的正文为准。
